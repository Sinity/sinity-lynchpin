# Campaign evidence

`lynchpin_project(action="campaign_evidence", project=..., bead_refs=[...], task_snapshot=...)` joins explicitly selected Beads obligations to structured owner records. `campaign_progress` returns the same product. Canonical Beads references are `sinnix://projects/<project>/beads/<id>`. The task snapshot is the gateway Beads closure: `nodes`, `complete`, `coverage`, and `temporal` with requested selector, resolved revision, effective time, observation time, known time, and watermark. Normalized Beads rows with `fields` are also accepted.

The read adapter calls `agentctl batch list --project <project> --json`. It consumes retained public batch records, worker results, integrated candidates, acceptance records, and the GitHub observations included by that owner route. It never reads runtime manifests or private receipt files directly. Retained batches are incomplete attempt history: an absent attempt remains unknown. Runtime result versions without explicit provenance remain usable as partial evidence.

The response uses the standard MCP envelope `{ok, data, meta}`. `data` contains `schema_version`, `product`, `project`, `bead_refs`, `items`, `counts`, `temporal`, `sources`, `session_evidence`, and `gaps`. Each item keeps `task_status` separate from `evidence_state`, includes its selected task revision, structured acceptance criteria, attempts, evidence chain, and missing evidence. Task closure alone does not prove acceptance. Evidence states are `verified`, `implementation_landed_ac_incomplete`, `attempted`, `unstarted`, `superseded`, `decomposed`, and `unknown`. `unstarted` requires complete attempt coverage, which the retained-batch adapter does not claim.

An acceptance criterion is verified only when its stable ID and selected obligation revision match the owner dispatch revision and a structured claim, an AC-linked passing receipt names the integrated candidate as `tested_sha`, and the owner records publication of that same candidate. The worker receipt must match the owner's candidate verification reference or job ID; the owner must attest the same tested SHA, a clean checkout, and a successful result. Missing owner corroboration stays unknown. AgentCTL v2 publishes `beads[].bead_revision`, `criteria[].ac_id`, and `verification[].{tested_sha,status,coverage:{ac_ids,scope},receipt}`. A test of a different worker SHA does not verify the integrated candidate. Contradictory satisfied and unsatisfied claims remain visible. Freeform acceptance text, missing IDs, duplicate IDs, missing revisions, and unsupported supersession claims cannot establish completion.

Per-source revisions, observation times, and watermarks remain independent. Digests of public observations are labeled `observation_digest`; they are not owner revisions. These products read owner snapshots, not a DuckDB generation. A supplied `refresh_id` is echoed as a requested generation with a coverage gap, never claimed as the generation that served the result. Historical selectors bound evidence by their timestamp, or by the resolved revision's effective time. Later acceptance is excluded; missing historical timestamps leave proof unknown.

Runtime `parent_session_ref` and `child_session_ref` values beginning with `session:` may add the stable `SyncPolylogue.get_session_orchestration` product. At most 50 explicit session references are read, with any truncation reported. Each session retains its own coverage and raw revision evidence. The archive's observations remain separate from a worker's claimed correlation to that session. Missing facade support or archive records is reported as unavailable. Session activity does not establish acceptance or publication. Lynchpin never scrapes Polylogue's disposable `.cache/verify` data. Worker model and usage fields stay under `worker_claim`; observed attempt values come only from owner provenance. Campaign usage totals remain null because shared multi-bead attempts do not define additive per-bead usage. Every native launch record is retained; historical results absent from the owner response remain explicitly unavailable.

`campaign_scope_delta` accepts `baseline_snapshot` and `task_snapshot`. It retains baseline obligations even after decomposition and records added, missing, removed, reopened, superseded, decomposed, and acceptance-revised rows. Closure `provenance_edges` supplies `discovered_from`, `split_from`, `supersedes`, and `residual_of` separately from membership edges. Native source-to-origin direction and `provenance_coverage` are preserved; provenance never expands the selected task set. A `discovered_from` source is a discovered defect only when its native issue type is `bug`; otherwise it is discovered work. Splits retain the original obligation without claiming that decomposition transferred or satisfied every criterion. Unresolved external endpoints remain visible. Explicit legacy metadata remains a fallback, and titles never infer scope roles or discoveries. Creation timing is separate from membership and provenance, using a requested timestamp when present and otherwise the resolved snapshot time.

Executable counts require `metadata.closure_role` to declare `work`, `leaf`, or `executable`; gate and decision roles may also be native issue types. Exact totals require complete scope and complete role coverage. Leaf counts additionally require explicit leaf roles or the owner's graph-leaf census. `baseline_closed_leaves` counts closed baseline leaves at baseline; `starting_leaves_closed_at_target` counts the original leaves closed at target; `starting_open_leaves_closed_at_target` counts the initially open subset that is closed at target. `newly_created_leaves` requires complete creation timestamps within the selected baseline/target bounds. Each missing denominator remains null independently. Observed counts remain labeled as observed. Task remaining counts open status; evidence remaining stays unknown until acceptance evidence has been joined.

`verification_regression` and `project_trajectory` read the same retained project batch route, optionally filtered by explicit `bead_refs`. Verification comparisons group exact command, coverage scope, AC IDs, and Beads revision. Observations keep tested SHA, receipt, source reference, and result or acceptance observation time. Worker-reported changes remain reported changes; owner-corroborated outcomes are labeled separately. Unknown or tied timestamps cannot establish an ordered regression. Trajectory counts distinct retained worker attempts and published batches, with explicit time bases and undated records. Each attempt names its actual recorded timestamp or the batch-creation lower-bound fallback; aggregate metadata reports the observed bases and marks mixed clocks. A shared worker or batch is counted once across multiple Beads. Neither product claims complete throughput or causation. They return `outcome="partial"` for bounded records and `outcome="unavailable"` when no usable records exist.
